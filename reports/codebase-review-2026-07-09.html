Swagger uses a public PKCE client without a secret

Implemented

What changed

  • clientSecret was removed from Swagger initialization and from API runtime settings.
  • OIDC_DOCS_CLIENT_ID=fastapi-docs selects a public client.
  • Both Keycloak realm exports define that client with standard flow enabled, direct grants disabled, and S256 PKCE required.
  • An audience mapper adds fastapi-client to the access token so the existing API validator accepts the login token.

Why login still works

The browser sends the authorization code plus its PKCE verifier to the token endpoint; no client secret is expected from a public client. The existing confidential fastapi-client remains available for scenario-test token acquisition.

04

Entity pagination has one safe, user-selected ordering

Implemented

The route uses enums rather than passing arbitrary column text into SQL. Every entity-table column except id is represented, and invalid values return the existing 400 validation problem.

Important constraint: ordering by a non-unique column cannot mathematically guarantee stable boundaries when values tie or rows change between requests. The requested one-column/no-ID contract is implemented; a unique tie-breaker or cursor would be needed for strict determinism.

API contract
GET /entities/?
  offset=0&limit=25&
  order_by=name&
  order_direction=desc

order_by ∈ {
  name, description,
  created_at, updated_at
}

Exactly one column; id is rejected.

A

OIDC discovery runs at application startup — inside lifespan

Implemented

Imports are now network-free. AuthNSettings contains only environment input, while immutable OIDCMetadata is resolved asynchronously before the lifespan yields readiness.

Implemented behavior

  • Discovery uses httpx.AsyncClient with explicit timeouts, three bounded attempts, and backoff.
  • The discovered issuer must exactly match the configured public issuer.
  • Compose can fetch discovery through the internal Keycloak address while retaining public browser endpoints and rewriting only the JWKS URL for container access.
  • A complete four-endpoint override bypasses discovery; partial override groups fail settings validation.
  • Lifespan constructs an app-scoped AccessTokenValidator; request dependencies retrieve it from request.app.state. There is no mutable module-level authentication state.
  • OpenAPI rendering reads the same app-scoped metadata to publish the discovered authorization and token endpoints.
  • Exhausted discovery retries fail startup, so the service never becomes ready with partial trust configuration.

Sources: FastAPI lifespan events; OpenID Connect Discovery 1.0.

Implemented lifecycle
1. Python imports modules
   no network I/O

2. FastAPI lifespan starts
   configure logging
   await resolve_oidc_metadata()
   validate issuer + required fields
   create auth runtime / JWKS client

3. Mark application ready
   yield

4. Serve requests

Failure policy:
bounded retry → explicit startup failure
never partially configured auth

Concrete template identity and parallel-Compose solution

Implemented

Template identity

The package description now exactly matches the GitHub repository description. The README includes an adopter checklist for package metadata, image names, OIDC clients, ports, and observability identifiers.

Compose portability

All fixed container_name values are removed. Host ports, public URLs, default image tags, and the optional Compose project name are configurable, while service-to-service DNS remains db and keycloak.

Exact login callback per stack

A one-shot keycloak-config service uses Keycloak's Admin REST API through httpx to register the exact Swagger redirect URI and web origin derived from APP_PUBLIC_URL. The application waits for this configuration before startup. This supports parallel stacks without production wildcard callbacks.

  • Run each stack with a distinct COMPOSE_PROJECT_NAME.
  • Assign unique APP_PORT and KEYCLOAK_PORT values.
  • Set matching APP_PUBLIC_URL and OIDC_PUBLIC_URL values.
  • Default API and migration images are also project-scoped, preventing worktrees from overwriting a shared :local tag.
  • Keep internal database, discovery, and JWKS traffic on Compose service DNS.

E

Why the Keycloak client configurator is under .docker

Infrastructure boundary

configure_keycloak_client.py is Compose bootstrap infrastructure, not application authentication code. It changes the development Keycloak server before the API starts; it does not discover OIDC metadata, validate tokens, or participate in request handling.

Why a script is needed

  • The checked-in realm export is static, but a parallel stack chooses its public application URL and port at runtime.
  • Keycloak should receive an exact Swagger callback such as http://localhost:8081/docs/oauth2-redirect. A static realm file cannot know that value, and using a broad wildcard would weaken redirect validation.
  • The one-shot keycloak-config service waits for Keycloak health, obtains an admin token, finds the fastapi-docs client, and updates only its redirect URI and web origin.
  • The API depends on that one-shot service completing successfully, so Swagger login configuration is ready before the API becomes available.

Why it belongs in .docker

The file is mounted only into the Compose bootstrap container. The production API image copies app/, not .docker/, so this Keycloak-specific local-environment concern stays outside the application package and production runtime. In a production platform, the equivalent configuration should normally be owned by identity-provider automation or infrastructure as code; this script is the self-contained local-template equivalent.

Naming alignment

The file configure_keycloak_client.py now exposes configure_keycloak_client(); its helper is named _get_keycloak_client_representation(). The names describe both the operation and the Keycloak Admin API object being handled.
